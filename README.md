# SovaGrid Agent

Unprivileged Linux agent for Ubuntu. It reads host metrics from `/proc` and the root filesystem, then pushes them to SovaGrid Hub over verified HTTPS. It uses only Python 3 standard-library modules and opens no listening port. Remote command polling is **disabled by default**.

## Install on Ubuntu

Python 3.10 or newer is required. Register the server in SovaGrid Hub first; the registration response contains a `server_id` and one-time `agent_token`.

```sh
sudo useradd --system --home-dir /var/lib/sovagrid-agent --shell /usr/sbin/nologin sovagrid
sudo install -d -o sovagrid -g sovagrid -m 0700 /var/lib/sovagrid-agent
sudo install -d -m 0755 /opt/sovagrid-agent
sudo cp -R sovagrid_agent /opt/sovagrid-agent/
sudo chown -R root:root /opt/sovagrid-agent
sudo install -d -o root -g sovagrid -m 0750 /etc/sovagrid
sudo install -o root -g sovagrid -m 0640 deploy/agent.json.example /etc/sovagrid/agent.json
sudo install -o root -g sovagrid -m 0640 /dev/null /etc/sovagrid/agent.token
```

Edit `/etc/sovagrid/agent.json`: set the actual HTTPS Hub origin and server ID. Put the one-time agent token in `/etc/sovagrid/agent.token` using a secure editor or file transfer, not a shell command recorded in history. Keep both files out of Git. Then:

```sh
sudo cp deploy/sovagrid-agent.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now sovagrid-agent
sudo systemctl status sovagrid-agent
```

The systemd unit runs as the `sovagrid` OS user without extra capabilities. It restricts filesystem writes to `/var/lib/sovagrid-agent`; commands cannot gain root or sudo from Hub. The agent verifies the Hub's TLS certificate and rejects every HTTP redirect so its bearer token cannot be forwarded to another origin. For a private CA, set `ca_file` to an absolute path. Plain HTTP and disabling certificate verification are unsupported.

## Metrics and API contract

Every `interval_seconds` (default 30, allowed 5–3600), the agent POSTs JSON to `/api/v1/servers/{server_id}/metrics` with `Authorization: Bearer <agent_token>`. It sends:

| Field | Meaning |
| --- | --- |
| `collected_at` | Unix seconds UTC; Hub allows at most five minutes of clock skew |
| `cpu_percent` | CPU busy percentage from two `/proc/stat` snapshots |
| `memory_percent` | `1 - MemAvailable/MemTotal`, expressed 0–100 |
| `disk_percent` | Used share of root filesystem from `statvfs` when its type is on the local allowlist; otherwise `0` with `disk_total_bytes=0` |
| `network_rx_bytes`, `network_tx_bytes` | Cumulative non-loopback interface byte counters |
| `load1` | One-minute system load |
| `uptime_seconds` | `/proc/uptime` |
| `memory_total_bytes`, `memory_available_bytes`, `disk_total_bytes`, `disk_available_bytes` | Additional capacities |
| `details` | Optional fixed-schema categories described below |

`details` contains only these categories when available:

| Key | Shape |
| --- | --- |
| `swap` | `{total_bytes, free_bytes, used_percent}` |
| `filesystems` | Up to 16 `{mountpoint, fstype, total_bytes, available_bytes, used_percent, inodes_total, inodes_available, inodes_used_percent}` objects for supported local mounts from mountinfo and statvfs |
| `filesystems_truncated` | Boolean: `true` if a supported local mount could not be measured, the 16-row cap was reached, or rows were removed to keep the payload under 12 KiB. A missing mountpoint is never proof of recovery. |
| `interfaces` | Up to 16 `{name, rx_bytes, tx_bytes, rx_errors, tx_errors}` objects from `/proc/net/dev` |
| `load5`, `load15` | Five- and fifteen-minute load numbers |
| `processes` | `{running, blocked}` from `/proc/stat` |
| `top_processes` | Up to 10 `{pid, name, rss_bytes}` objects sorted by RSS. `name` comes only from the short `/proc/<pid>/comm` field; the agent never reads process `cmdline` or `environ` for metrics. |
| `disk_io` | Up to 16 `{device, read_bytes, write_bytes}` objects from `/sys/block/*/stat` when available |
| `cpu_times` | `{iowait_percent, steal_percent}` from the same two `/proc/stat` snapshots as `cpu_percent`; omitted if the interval or counters are invalid |
| `pressure` | Available `/proc/pressure/{cpu,memory,io}` resources: `cpu.some`, `memory.some/full`, `io.some/full`, each with `{avg10, avg60, avg300, total_us}`. A missing or malformed resource is omitted. |
| `services` | `{failed_count, units}` from a read-only, three-second-bounded `systemctl list-units`; up to 16 failed or watched services with `{name, active, sub}` |
| `journal_units` | When locally enabled, the exact list of up to 16 `.service` units the Web panel may request; no log text appears in metrics. |

The agent calls `statvfs` only for mounted `ext2/3/4`, `xfs`, `btrfs`, `f2fs`, `zfs`, `vfat`, `exfat`, `ntfs3`, and `tmpfs` filesystems (only root for `tmpfs`). It skips NFS, CIFS, FUSE, and unknown types to avoid blocking the polling loop. If the root mount is skipped, `disk_total_bytes=0` and `disk_percent=0` mean unavailable, so the root-disk alert cannot fire. A local filesystem stalled in the kernel can still block a synchronous `statvfs`; this is not a hard real-time sampler. The agent excludes loop/ram devices and the loopback interface. It bounds names, list sizes, and the serialized `details` object to 12 KiB; no arbitrary labels, logs, credentials, or command text are added to metrics. Process RSS counts resident pages and can include shared pages; it is not private memory, and one snapshot cannot provide a reliable per-process CPU percentage. Process names are short, process-controlled labels, so use neutral names on hosts where even a process title is sensitive. Interface totals may count virtual devices, and stacked block devices such as device mapper can represent the same underlying I/O more than once. Disk I/O values are cumulative 512-byte-sector counters converted to bytes.

The Hub replies `202 {"accepted":true,"metric_details":["pressure","cpu_times"]}` when it supports the new categories. The Agent sends neither category until a valid response advertises it. The `filesystems_truncated` flag is sent to current Hubs immediately so an incomplete inventory cannot be treated as recovery. If an older Hub rejects that field, or a Hub rollback rejects previously advertised categories, one `422` causes a single retry without those extensions while preserving the filesystem inventory and core metrics. The Agent tries the complete report again on its next sample, so it detects a Hub upgrade without a restart. A second `422` is reported as an error; no further retries are made for that sample. On other failures, the agent logs a generic error and retries with bounded exponential backoff. It never logs tokens. Cumulative counters may reset on reboot or device replacement; consumers should calculate rates accordingly. `iowait_percent` is an approximate kernel CPU accounting value, not disk utilization. All samples go to the Hub API; there is no direct SSH or inbound metrics endpoint.

Earlier categories such as `top_processes` still require a Hub version that recognizes them. `/proc` permissions may limit which processes the unprivileged Agent can read; no extra privileges are requested to fill the table.

## Optional remote VPN inventory

When the separate SovaGrid VPN status timer is installed on this Ubuntu host, it writes `/var/lib/sovagrid-vpn-inventory/status.json` as `root:sovagrid`, with directory mode `0750` and file mode `0640`. Agent reads this one fixed file after sending normal metrics. It rejects a symlink, wrong owner/group or mode, inode replacement during the read, a file larger than 64 KiB, duplicate JSON fields, and snapshots more than 90 seconds old according to this host's clock. It never opens VPN profiles, private keys, Docker sockets, or arbitrary paths. Agent removes unknown fields from the snapshot before its separate `POST /api/v1/servers/{server_id}/vpn` using the existing Agent bearer token and verified HTTPS. Hub applies its own strict public VPN projector before persistence. An older Hub's `404`, a missing status timer, or a failed VPN refresh does not interrupt metrics or command processing. The corresponding viewer API is documented in the Hub [API](../sovagrid-hub/API.md).

## Optional read-only Docker and Podman inventory

On a managed Ubuntu host, `sudo ./run.sh --with-containers` installs a separate root-owned one-shot collector and 30-second timer. Subsequent managed upgrades preserve this opt-in. `sudo ./run.sh --disable-containers` removes the timer and snapshot. The Agent remains outside the `docker` and `podman` groups, and neither Agent nor Hub receives an Engine socket. Only the isolated collector joins the `docker` group to read the local socket; its systemd service drops Linux capabilities and can write only its private snapshot directory. The collector checks only the fixed rootful `/run/docker.sock` and `/run/podman/podman.sock` Unix sockets; it never starts a daemon or enters a rootless user's runtime directory. Each source independently reports `source_status=ok|unavailable` and, when unavailable, a fixed `no_socket`, `no_access`, or `error` reason.

The collector uses bounded local read-only Engine API GETs for at most 12 containers per source. It copies only full ID, name, image, state, health, restart count, and CPU/RAM when available into a root-owned, Agent-group-readable 10 KiB snapshot. Raw inspect and stats responses may contain secrets, but are held only in collector memory and never logged, sent, or saved. The inventory does not expose labels, environment, command, mounts, network or actions. The Agent checks snapshot owner, mode, file type, size and schema before including it in `details.containers`; an absent or invalid snapshot does not block ordinary host metrics. The Web panel shows the snapshot's UTC time and marks old or offline data stale. Rootless Podman and nondefault Engine sockets are currently reported as unavailable.

On a promoted host with a separate local Agent, `sovagrid-container-inventory-local.service` and its timer provide an isolated snapshot under `/var/lib/sovagrid-containers-local/snapshot.json`, owned by `root:sovagrid-local`. Its collector has only the fixed `--local` profile. The local Agent reads that snapshot only when its effective UID and primary GID exactly match `sovagrid-local`; the external `sovagrid` Agent continues to read the standard snapshot. This source support does not enable the local timer automatically. The host installer must install and start its root-owned unit and private directory explicitly.

### Managed container logs backend

The dedicated container-log request requires both the container inventory opt-in and the host Agent's root-only service broker socket. It accepts only a full 64-character ID from a fresh, complete inventory. The broker independently inspects that ID and requires Compose labels `com.docker.compose.project=sovagrid`, service `hub` or `web`, and the matching SovaGrid image before making a fixed read-only Engine API log GET. It never accepts a name or partial ID, follows a stream, or executes in a container. Up to 100 lines and 8192 UTF-8 bytes may leave the broker; binary, NUL and terminal control output is denied. Rootless sockets and non-SovaGrid containers are not eligible.

### Container action broker prerequisite

The root service broker now understands a separate canonical `container_action` request for `status`, `start`, `stop`, or `restart` on an exact Docker container ID. Agent reserves the exact `/usr/local/bin/sovagrid-container-action-ctl ACTION docker FULL_64_HEX_ID` job marker and rejects every malformed occurrence before shell execution. This remains a **disabled backend prerequisite**: neither installation script creates its policy, so adding a Hub route alone cannot arm it. No live host is armed by an upgrade. The existing inventory and log features remain read-only.

The default socket requires a root-owned `0700` `/etc/sovagrid-container-actions` directory containing separate root-owned `0600` `enabled` (`enabled\n`) and `policy.json` files. The local Agent socket uses a completely separate, likewise absent `/etc/sovagrid-container-actions-local` policy. The policy has version `1` and at most 16 entries, each with exact full `id`, Docker `name`, immutable `image_id` (`sha256:` plus 64 lowercase hex digits), and an action list including `status`. The broker re-reads the selected root policy on each request and independently checks the live inspect ID, name, image ID, Compose identity, privilege and namespaces before any action. SovaGrid, Amnezia, SSH, tunnels, container engines and other protected infrastructure are denied even if allowlisted. Any bind or volume mount, `VolumesFrom`, extra capability, device, custom security option or host namespace denies the action; incomplete isolation metadata also denies it. This conservative rule includes stateless `status` requests, while the ordinary inventory remains available for all containers. Only fixed Docker Engine API endpoints on `/run/docker.sock` are used; the Agent and Hub never receive that socket. The broker checks the caller's `SO_PEERCRED` UID and systemd MainPID, including immediately before each mutation. Responses have only action, ID, result and state; uncertain mutations are never described as preserved or safe to retry. Mutation attempts and outcomes are written to the root broker journal without Engine response contents. Both policies should remain absent until structured Hub authorization, durable job provenance, and administrative setup workflows are implemented and reviewed.

The Hub's dedicated administrator request keeps log text only in memory for the initiating session and never writes it to metrics history, jobs or audit details. The backend has no Web control yet. An administrator who can run arbitrary Agent shell commands has the same Unix UID as the Agent and can directly access its allowed broker sockets; that broader existing command privilege can produce a persistent ordinary job result. A separate command UID is required to enforce transient-only storage against such an administrator.

## HTTP, HTTPS, TCP and DNS monitoring checks

The long-running Agent starts two independent check workers, each with its own HTTPS Hub client, without enabling remote commands. `--once` sends metrics only. Configure explicit targets in the Hub Web panel: HTTP/HTTPS GET, TCP connect or DNS A/AAAA resolution, an interval of 60–3600 seconds, and a timeout of 1–10 seconds. DNS uses this Agent's operating-system resolver and can require one expected IP or accept any answer of the selected family. No targets are created automatically. Private and loopback targets are allowed because a check measures connectivity from this Agent. Unspecified, multicast, scoped IPv6 and noncanonical numeric host aliases are rejected.

Workers POST `{"protocol":1}` to `/api/v1/servers/{server_id}/checks/claim` and report only typed status, latency, HTTP status, verified TLS expiry and a fixed error code to `/checks/{check_id}/result`, together with the lease ID and configuration revision. Empty claims wait 15 seconds; an older Hub returning 404 or 405 backs off for five minutes. These requests never add a category to `metric.details` or join the command, terminal or file queues. Hub handles scheduling and bounded history; a stale or cancelled lease cannot publish against a newer configuration. Lease expiry is authoritative on the Hub clock: Agent accepts up to five minutes of clock skew when validating a claim, while each target still has its independent monotonic 1–10 second deadline and Hub rejects expired results.

Each target runs in a fixed, isolated Python helper with a minimal environment and no Hub credentials. At most two helpers run at once. The parent bounds their entire lifetime, including stalled DNS, to the configured timeout and reads no more than 4 KiB of helper output. Linux arms `PR_SET_PDEATHSIG` inside the exec'd helper and checks its parent PID, so an Agent death also kills a blocked helper. Normal cancellation kills and reaps each helper; command cleanup reserves these children from its separate subreaper scans. The packaged code must remain root-owned as in the installation above.

HTTP sends GET without authentication, cookies, proxy settings or redirects. It reads at most 32 KiB of status lines and headers in total, then closes without reading the response body; only 2xx is up. HTTPS uses the system trust store and standard hostname/certificate verification. An HTTPS definition may additionally carry `ca_cert_der_b64`: canonical base64 of one X.509 DER CA certificate, at most 1536 decoded bytes. Agent validates its format and adds it to the probe trust store; certificate chain and hostname verification remain mandatory. `notAfter` is returned only after verification; an expired, untrusted or mismatched certificate reports `tls_error`. The Agent's private `ca_file` for its connection to Hub is separate from a target CA override. TCP sends no protocol bytes, so a successful connect proves only that the port accepts connections. DNS sends no connection to a returned IP and reports `dns_error` or `dns_mismatch` without exposing answer addresses. Responses, target addresses, resolved IPs, status phrases, headers and exception text never enter a result or log. Target definitions remain administrator configuration in Hub.

The check tests use disposable local HTTP/TCP/TLS servers and a temporary OpenSSL-generated CA, including custom-CA success and wrong-CA/hostname failures, expiry, body/header limits, DNS deadlines, worker cancellation, old-Hub backoff and command-child isolation. Linux CI also verifies helper termination when its parent dies.

## Remote commands

This capability is explicit opt-in on **both** sides:

1. An admin sets `remote_commands_enabled=true` for the server in Hub (`POST /api/v1/servers/{id}/commands` with `{"enabled":true}`).
2. A local administrator edits `/etc/sovagrid/agent.json` to set `"allow_remote_commands": true` and restarts the agent.

Only then does the agent poll `GET /api/v1/servers/{id}/jobs/next` after each successful metric upload. A job can come from either a bound Telegram `admin` using `/exec <server_id> <command>` and `/confirm <code>` within 60 seconds, or the logged-in Hub admin using `POST /api/v1/servers/{id}/jobs` with `{ "command": "…" }`. Hub enforces a 2048-byte UTF-8 command cap, 15-second timeout for ordinary jobs, and fixed 8 KiB output cap. Ordinary commands remain capped at 15 seconds and execute through `/bin/sh -c` as the `sovagrid` OS user, with a minimal environment and no stdin. The agent sends the result to `POST /api/v1/servers/{id}/jobs/{job_id}/result` as `{ "state", "exit_code", "output" }`. States are `succeeded`, `failed`, `timed_out`, and `output_limited`.

The dedicated process-inventory request uses an exact reserved marker and never enters the shell. On demand, Agent reads only `/proc/<pid>/comm` and `statm` as its unprivileged user, returning up to 32 PID-sorted names and RSS values. It enumerates PID names with a five-second budget and reads at most 2048 process directories per page; a name filter and `next_after_pid` cursor support traversal. Process command lines, environments, paths, and user names are never read. This response is separate from metrics, and Hub keeps the page only in a short-lived, session-bound memory cache. Live process changes can cause additions or omissions across pages.

Managed WireGuard actions from Hub reserve the exact `/usr/local/bin/sovagrid-vpn-ctl` command syntax. The Agent accepts only one canonical invocation with these actions: `create NAME --port PORT --subnet CIDR --endpoint HOST`, `activate NAME`, `add-client NAME CLIENT`, `revoke-client NAME CLIENT`, `sealed-export NAME CLIENT PUBLIC_KEY`, or `remove NAME --confirm-name NAME`. `PUBLIC_KEY` must be the canonical unpadded base64url encoding of a 65-byte uncompressed P-256 point. Agent checks the same narrow name, port, private subnet, and endpoint syntax as Hub, then sends a bounded JSON request directly from its long-running process to the fixed root broker socket. The CLI marker is never run as a child process or shell command. The broker bounds its transaction to 95 seconds and Agent waits at most 100 seconds for the response. A successful sealed export passes along only a validated five-field ciphertext envelope; failed or malformed broker output becomes a fixed error, never plaintext in Hub's job record. A lost reply to a mutating request is reported as uncertain so users inspect state before retrying. After an extended job, Agent refreshes metrics before reporting the result to reduce false offline alerts; a failed refresh is logged without request details and does not discard the result. A malformed command containing the broker path is rejected before execution and reported as failed. A missing or inaccessible broker socket produces a sanitized job result instead of leaving the Hub job delivered. Agent still runs unprivileged under `NoNewPrivileges=true`; the broker socket and its root service enforce privileged operations.

Optional Amnezia control reserves the exact `/usr/local/bin/sovagrid-amnezia-ctl` command syntax for `status TARGET`, `settings-preview TARGET`, `add-profile TARGET CLIENT ADDRESS ENDPOINT PUBLIC_KEY --route split|full`, `sealed-export TARGET CLIENT PUBLIC_KEY`, or `revoke TARGET CLIENT`, where `TARGET` is `awg2` or `wireguard`. Agent validates the complete argument list and sends a bounded JSON request directly from its long-running process to the root broker's fixed Unix socket; the marker is never run as a child process. The broker's own operation bound is 120 seconds and Agent's response wait is 130 seconds. Agent requires the returned target to match the requested one and accepts only `awg3-conf` for AWG2 or `wg-conf` for standard WireGuard. It forwards only a whitelisted status, read-only settings preview (at most 4096 bytes), result, or authenticated ciphertext envelope; errors and malformed output become fixed messages. A lost reply to a mutation is reported as uncertain so users inspect state before retrying. The preview includes only server network settings, client counts, numeric AWG fields, and pinned digests, without keys or client identities. The client and root broker are installed and armed separately on the host. An absent or disarmed socket has no effect on normal Agent metrics, commands, terminal, or files. Amnezia enrolment and recovery are deliberately local root operations, never Agent jobs. AWG3 numeric settings use exact `settings-plan`, `settings-intent` and `settings-apply` commands for `awg2` only. The intent returns a five-minute one-use confirmation handle for a pinned old config digest, generation, proposed digest and canonical numeric patch; applying it requires the same pins and handle. The root broker admits only zero-client, unchanged-port changes and verifies the running selectors after a journaled sync. Agent validates the complete command and whitelists the response, including exact digest/generation binding, before sending a Hub job result. A lost reply to intent or apply is uncertain and requires fresh status/plan inspection. The confirmation handle appears in the admin Hub job history during its short validity, so it is a confirmation step rather than a long-term secret.

### Optional service control backend

Agent recognises exactly `/usr/local/bin/sovagrid-service-ctl ACTION UNIT`, where `ACTION` is `status`, `start`, `stop`, or `restart`, and `UNIT` is a single exact `.service` name. This path is a reserved protocol marker, not an executable. The command never enters the ordinary shell. Agent asks `/run/sovagrid-service/control.sock`, then forwards only `action`, `unit`, `result`, `load_state`, `active_state`, and `sub_state` in the normal job output. A mutation timeout, lost broker reply, nonzero `systemctl` result, or mismatch with the observed service state is `uncertain`: it may already have changed the unit, so request a fresh status before retrying. Hub's structured service route and Connect's managed setup use this backend; they are part of the pending common server/client release.

The root broker is disabled by default. The normal Agent uses `/etc/sovagrid-service`, while a separate local Agent on a promoted Hub host uses `/etc/sovagrid-service-local`. Each policy directory is root-owned mode `0700` and contains an `enabled` marker with exact bytes `enabled\n` and a `units.json` policy, both root-owned mode `0600`. The policy is a JSON object such as `{"version":1,"units":{"nginx.service":["status","restart"]}}`, with at most 16 exact units and a separate nonempty action list for each. The broker selects the policy by its inherited socket and re-reads it for every request. The setup rejects mutation permissions for SovaGrid, SSH, tunnel, network, container-engine, firewall and VPN access units; status remains available. The broker independently blocks those mutations even when reading an old policy and verifies the systemd unit ID and every alias immediately before an allowed mutation. A changed, missing or ambiguous identity fails without running the action. Run the root-only `/usr/bin/python3 -B -E -S -m sovagrid_agent.service_setup` from the installed Agent tree; `-B` keeps preview from writing Python bytecode. It offers `preview`, `preview --profile default|local` with a proposed policy JSON on stdin, `arm --profile default|local --expected-state REVISION` with that policy on stdin, and `disarm --profile default|local|all --expected-state REVISION` (`default` when omitted). Preview reports both profiles and their state revision. Mutations compare that revision under a root lock. Arm checks the selected installed Python tree is not Agent-writable, installs exact unit files, and writes only that profile's marker after its socket works. Local arm also adds the fixed service socket to the promoted Agent's canonical config and restarts only that Agent. Failed changes restore policy, units, socket state and local config; if rollback fails, the marker stays absent. Both profiles can run independently. The setup helper never runs automatically.

The default socket is owned by `sovagrid` with mode `0600`; the root broker requires `SO_PEERCRED` UID and PID to match the exact `sovagrid-agent.service` MainPID reported by the root-owned systemd manager. For an independently promoted `sovagrid-local` Agent, choose the local profile and set `"service_socket":"/run/sovagrid-service-local/control.sock"` in its Agent config; that socket is owned only by `sovagrid-local` and requires the `sovagrid-agent-local.service` MainPID. This check applies to status and mutation, and fails closed when systemd reports zero, an error, or a changed PID. Agent also starts with `PR_SET_DUMPABLE=0`, verified before reading jobs, so same-UID command children cannot ptrace its memory or borrow its file descriptors. Agent config accepts only the two fixed socket paths. The broker launches only `/usr/bin/systemctl --system --no-ask-password` with fixed arguments. `status` uses `systemctl show` and accepts only four explicit properties, including a matching unit ID; mutation preflight separately checks `Id`, `Names` and `LoadState=loaded` with a five-second bound, then checks MainPID again immediately before the action. If systemd omits aliases or presents a protected alias, no mutation runs. Raw stdout and stderr never reach Hub. Missing marker, policy, socket, or an unlisted action fails closed. Do not arm mutation policy until the deployed Agent and broker both support this PID boundary. The live policies remain status-only until separately changed by a host administrator.

Commands are delivered at most once. If the agent crashes after fetching one, the Hub leaves its state as `delivered` and requires a human to decide whether to retry. Hub and Telegram admins can read anything accessible to the `sovagrid` user, including the agent's own local token; grant these roles only to trusted people and avoid sending credentials through commands or their output. Queued web jobs are cancelled if the issuing Hub session logs out, expires, or is revoked by a password change. A job already delivered to the agent can still finish. Hub's `remote_commands_enabled` flag does not prove that the local agent flag is on; if a job remains `queued`, inspect the local agent config and service logs.

On Linux, the agent starts one-shot job shells in their own process groups, tracks descendants in `/proc`, and asks the kernel to make the agent a child subreaper so it can also find orphaned descendants that start a new session. At job completion, timeout, or output limit, it kills observed descendants after checking each PID's start time. This is a best-effort bound, not a containment boundary: a process can fork and escape between scans, the subreaper request may fail, and an uninterruptible kernel task cannot be killed promptly. Use a dedicated low-privilege OS user and systemd restrictions; stronger containment requires a cgroup or container policy.

## Read-only systemd journal in Web

Journal access has its own local opt-in and is off by default. In `/etc/sovagrid/agent.json`, configure an exact list of 1–16 service unit names and enable it only after reviewing what those logs may contain:

```json
"allow_remote_commands": true,
"allow_systemd_journal": true,
"journal_units": ["sovagrid-agent.service", "ssh.service"]
```

The selected server must also have Hub remote commands enabled. Agent reports the allowed names in its authenticated metrics, so the Web selector shows only those names. A request outside that list, or any malformed request containing the reserved journal marker, is rejected before process creation. Agent never launches `journalctl` from a general job. It sends one canonical `{ "unit", "lines" }` request over `/run/sovagrid-journal/control.sock` to an independently installed, socket-activated broker. The broker checks the caller's Unix UID with `SO_PEERCRED`, re-reads its own root-owned policy on every request, and launches `/usr/bin/journalctl` with a fixed argument vector and no shell. It reads at most 100 lines from the last 24 hours, with a five-second deadline and 8 KiB output cap. This feature never grants root, sudo, or `systemctl start/stop/restart`.

The broker runs as the separate `sovagrid-journal` OS user. Only that identity has `systemd-journal` group access; **do not add `sovagrid` to `systemd-journal` or `adm`**, because ordinary remote commands could then read all journal units directly. The broker refuses to start if the Agent account is in either group. Its policy is `/etc/sovagrid-journal/units.json`, with exactly `{ "units": ["ssh.service"] }` or another 1–16 unique, exact `.service` list. The directory must be `root:sovagrid-journal 0750` and the file `root:sovagrid-journal 0640`. The socket is owned by `sovagrid` with mode `0600`. Install `deploy/sovagrid-journal-control.socket` and `.service` under `/etc/systemd/system/`, reload systemd, then enable and start **only the socket**. The broker service starts on demand; the Agent configuration and broker policy both need the selected unit. A missing socket or policy returns a bounded error in the panel. Restart Agent after changing its local config; the broker reads policy changes on its next request. For this **structured Logs action**, Hub holds at most 32 journal outputs of 8 KiB each in memory for five minutes, exposes each only to its initiating admin session, and never saves journal text in SQLite or audit events. Logout, password change, or Hub restart clears it earlier. A trusted admin with general command access also runs commands as `sovagrid` and can reach the broker socket for allowed units; output from a general command uses the usual persistent job history. The broker's root policy still prevents access to other journal units.

## Interactive browser terminal

Interactive PTY polling is off by default. It starts only when `allow_remote_commands` and `allow_interactive_terminal` are both `true` in `/etc/sovagrid/agent.json`, the Hub server has `remote_commands_enabled=true`, and the optional local broker is installed. The standard [blueprint installer](../sovagrid-blueprint/DEPLOY.md) provides `sudo ./run.sh --with-terminal` for this setup. A manual installation must create a separate `sovagrid-shell` user and group outside the `sovagrid` group, a private `/var/lib/sovagrid-shell`, and install and start `deploy/sovagrid-terminal-control.socket` and `.service`. Ensure `sovagrid-shell` cannot read `/etc/sovagrid/agent.token` before enabling the flags.

The broker accepts only a bounded `{cols,rows}` request over `/run/sovagrid-terminal/control.sock` from the exact `sovagrid` Unix UID, checked with `SO_PEERCRED`. Systemd opens the root-owned listener and starts the broker itself as `sovagrid-shell` with an empty capability set. It creates `/bin/bash --noprofile --norc -i` under that same identity and passes the PTY master FD to Agent with `SCM_RIGHTS`. Its systemd cgroup terminates active shells on service stop or restart. The shell has a 30-minute hard lifetime and is killed when Agent disconnects. Neither broker nor Agent logs PTY bytes; Hub keeps them only in bounded memory. This terminal can use ordinary network sockets and the shell user's own files, but it has no Agent token, sudo access, or general root administration authority.

An Agent promoted alongside an existing remote Agent uses a separate fixed profile: `terminal_socket` is `/run/sovagrid-terminal-local/control.sock`; `sovagrid-terminal-local-control.socket` accepts only the `sovagrid-local` Unix UID; and `sovagrid-terminal-local-control.service` runs shells as `sovagrid-local-shell` in `/var/lib/sovagrid-local-shell`. The two profiles do not share Unix users, groups, sockets or shell homes. The `terminal_socket` config accepts only these two fixed SovaGrid paths. The local profile remains off until the host-root promotion helper explicitly enables it.

Agent opens only outbound verified HTTPS connections for terminal lease, controls, output, and exit. Hub enforces a single terminal per server, four globally, a 4 KiB frame cap, and 90 seconds of browser inactivity. A failed Hub request, local broker failure, or revoked permission closes the local PTY. Interactive input is separate from one-shot command jobs and never enters the metrics payload. The [Hub API](../sovagrid-hub/API.md) specifies sequence and retry semantics.

## Browser file manager

File access is disabled by default. To use it, create a dedicated private directory and set three local values in `/etc/sovagrid/agent.json`:

```sh
sudo install -d -o sovagrid -g sovagrid -m 0700 /var/lib/sovagrid-agent/files
```

```json
"allow_remote_commands": true,
"allow_file_manager": true,
"file_roots": {"workspace": "/var/lib/sovagrid-agent/files"}
```

Keep those entries inside the existing JSON object and restart `sovagrid-agent`. The Hub server must also have remote commands enabled. The default systemd unit allows writes only under `/var/lib/sovagrid-agent`; adding another writable root requires an explicit local service override for that exact directory. `ProtectHome=true` prevents `/home` access in the default unit. Do not put Agent tokens, VPN keys, or Hub data in a configured file root. Root aliases contain lowercase letters, digits, `_`, or `-` and are the only path information disclosed before browsing.

The Agent polls only outbound HTTPS for file requests. It never launches a shell for this feature and never runs the file operation as root. Every directory component is opened with `O_NOFOLLOW` from a trusted directory descriptor. Symlinks, hard-linked files, special files, and paths with `.` or `..` are rejected. The text editor accepts only UTF-8 without NUL and files up to 8 KiB. Binary downloads accept arbitrary bytes in 64 KiB chunks up to 32 MiB; uploads remain limited to 4 MiB. Downloads include a full SHA-256 digest checked by the browser. Uploads stay in Agent memory (at most four sessions, ten-minute idle expiry) until the declared size and SHA-256 match; only then does the Agent write a temporary file and atomically replace the destination. Agent restart discards unfinished uploads. Both text writes and binary uploads require an Agent-owned private parent directory. Binary overwrite also requires an Agent-owned regular file without hard links and the ETag shown at confirmation; new-file upload fails if the name has appeared meanwhile. Ordinary read and write permissions of the `sovagrid` user still apply. Hub keeps chunks only in bounded memory for at most 120 seconds, and the browser releases completed transfer results sooner. Neither Hub SQLite nor the audit contains paths or file bytes; audit keeps action, outcome, and a path hash. Avoid adding credential directories to `file_roots` because a Hub administrator can download anything the Agent user can read there.

## Local update-idle handshake (future external Agent update)

The standard Agent service enables a Unix socket at `/run/sovagrid-agent-control/agent.sock`; systemd creates its private runtime directory. Only a local root peer accepted by Linux `SO_PEERCRED` can request `QUIESCE 1`. The Agent pauses new job, file, terminal and network-check claims, waits for fetched work and network checks (including result delivery) to finish, and for all upload sessions and probe helper processes to end. It then returns one JSON line with protocol `1`, process PID, a random process epoch, and zero counts for `jobs_inflight`, `file_operations`, `terminal_sessions`, `network_checks`, `upload_sessions` and `probe_helpers`. Metrics continue while work is paused. A busy Agent returns `BUSY 1` after at most 180 seconds. The root client must send `PING 1` at intervals shorter than 45 seconds and verify `PONG 1 <epoch>`; the hold ends on `RELEASE 1`, disconnect, missed heartbeat, or its absolute 900-second limit.

Before trusting the ACK, a future root updater must compare the connected socket server's `SO_PEERCRED` PID and UID with `systemctl show` for `sovagrid-agent.service` (`MainPID` and `User`). It must keep that same socket open through the confirmed service stop and treat a lost `PONG`, changed epoch, or early disconnect as failure. This handshake is only one part of the external Agent update protocol; it does not enable live apply. Older external Agents without the socket cannot issue an idle ACK.

## External Agent trial gate (future update)

The ordinary service does not set trial environment variables. A future root updater may add a temporary systemd drop-in with `SOVAGRID_EXTERNAL_TRIAL_GATE=1` and a 32-character lowercase hexadecimal `SOVAGRID_EXTERNAL_TRIAL_EPOCH`. An incomplete or malformed pair stops Agent startup before Hub configuration or network work. The gate is a Unix socket at `/run/sovagrid-external-agent-trial/gate.sock` in a root-owned, `root:sovagrid 0710` directory; its socket is `root:sovagrid 0660`. Agent checks both with `lstat` and requires the connected peer's Linux `SO_PEERCRED` UID to be root.

The trial Agent sends `HELLO 1 <epoch>` and requires exact `READY 1 <epoch>`, then sends `PING 0` and requires `PONG 0` before constructing its Hub client. It repeats numbered challenges every two seconds and requires a reply within three seconds. EOF, wrong reply, lost root supervisor or a 900-second absolute trial lifetime terminates the process with status 70. During the trial it reports metrics only: it does not claim commands, terminal sessions, files or network checks. After a successful trial, the root updater must remove the drop-in and restart Agent in ordinary mode. The root-side update writer and rollback proof are still required before external-Agent live apply is enabled.
